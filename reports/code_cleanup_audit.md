## Code, imports, dependencies, and data flow

- Entry points include `app.py`, `scripts/download_datasets.py`,
  `scripts/inspect_datasets.py`, `scripts/build_database.py`,
  `scripts/export_tableau_data.py`, plus `f1-ingest` and `f1-transform`
  console scripts configured in `pyproject.toml`.
- The Kaggle path stages raw datasets, inspects them, builds the separate
  historical database, loads it through `f1_intelligence.analytics`, then
  feeds Streamlit or the Tableau extract exporter. The existing FastF1
  ingestion/transformation/storage path remains separate.
- All importable project modules and CLI modules imported successfully. Python
  syntax compilation succeeded. No broken import or circular dependency was
  observed in this check.
- An AST unused-import screen found no unused ordinary imports. Its only
  result was the expected `from __future__ import annotations` marker, which
  was excluded from the unused-import interpretation.
- An AST zero-reference screen initially flagged `reliability_summary` and
  `tyre_summary` in `src/f1_intelligence/analytics/__init__.py`.
  `reliability_summary` had the same status/entry aggregation as the
  Reliability page; the page now calls the shared helper, and a known-value
  test verifies entry and classified-finish counts. `tyre_summary` remains a
  reusable helper whose output/schema does not match the dashboard's narrower
  table; retain it rather than alter outputs or expand the refactor.
- Other zero-reference candidates are method/property names, protocol methods,
  or public CLI/service helpers whose use is through attribute access,
  `__main__`, console entry points, or external callers. Examples include
  `FastF1Source.get_event_schedule`, `FastF1Source.get_session`,
  `IngestionReport.has_failures` / `.extend`, `RequestController.call`,
  settings validators, and the `DataStore` protocol. A simple name-reference
  scan is not sufficient evidence to remove these; retain them.
- The Reliability page's repeated status-entry aggregation was consolidated
  to `reliability_summary`, preserving null-status exclusion and chart
  dimensions/order. Shared analytics helpers are also used for driver
  metrics, filter logic, result joins, and pit-stop attribution.
- No direct Python source import of NumPy was found, but the package declares
  it alongside Pandas, which depends on NumPy. Retain rather than change
  dependency resolution. `openpyxl`, `xlrd`, and `pyarrow` support dynamically
  selected Excel/Parquet readers; `fastf1`, `kagglehub`, `PyYAML`, `plotly`,
  and `streamlit` are used by runtime/CLI code. `pytest` is used by the test
  suite. No dependency is proven unnecessary.
- No overlapping active configuration files or abandoned experiment files
  were identified. Temporary database cleanup is the only high-confidence
  file removal found.

## Cleanup performed

- Removed `data/processed/.f1_intelligence.db.16060.tmp` only after confirming
  it was byte-identical to the canonical database, passed SQLite integrity
  checks, had the builder's temporary-file naming pattern, and was not held
  open. The canonical `data/processed/f1_intelligence.db` was retained.
- Reused `reliability_summary` for the dashboard's status-count chart instead
  of duplicating its grouping logic; added a known-value unit test.
- No raw datasets, canonical databases, exports, documentation, configuration,
  or dependencies were removed. No functions, classes, imports, or metric
  formulas were removed.
- No dependency versions were changed.

## Verification after cleanup

The complete test suite passed (46 tests; baseline was 45). Syntax/import
checks passed. The application rendered seven pages and both theme modes through Streamlit's
AppTest; the live Streamlit endpoint returned `ok`. Dataset inspection,
database loading and filter checks, and Tableau exports all completed
successfully. The isolated Tableau output retained the expected eight CSV
extracts and matching dictionaries. The canonical database passed SQLite
integrity and foreign-key checks.

## Final outcome and unresolved risks

One verified orphaned duplicate database temporary file was removed. The
audit report itself adds one file; therefore the current inventory is 115
files including this report (114 when excluding the new report), compared
with 115 before cleanup. The two sets of identical raw or placeholder files
remain intentionally. No code or dependency removals were justified by the
reference checks; uncertain/public API surfaces were kept.
There are no known cleanup regressions. The static AST screen is not a formal
whole-program analyzer, so its candidate findings were reviewed conservatively.
